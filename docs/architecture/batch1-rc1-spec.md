## 1. 第一法则与适用边界

凡改变参与资格、程序状态、资源配置或权利义务的决定与动作（含批准、拒绝、暂停、恢复、变更与取消），都必须绑定可解析、版本确定的授权、证据、适用范围和救济记录；生效或执行时必须重新核验相关权限与状态。缺失、过期、撤销或存在阻断性争议时，不得获得相应效力。

`DRAFT / SUBMITTED / EFFECTIVE / SUPERSEDED / WITHDRAWN` 表达记录生命周期，不替代案件或工单状态。草稿可以缺少领域材料，但必须有系统标识、归属和 ACL。提交允许材料不全；受理、回执、必要限流和隔离按服务端受理政策发生，不直接产生所请求的制度效力。匿名抗辩可使用服务端建立的受限匿名会话主体，不伪造实名或因此授予表决资格。

结构检查、事务内状态检查、具名实质适用性审查分别负责各自范围。系统保存判断依据，不承诺法律判断绝对正确、授权来源绝无造假或记录数学上不可篡改。

Batch 1 仅自动管理平台内尚未交接的工单、通知和复核流程。外部协查函可按明确权限生成人工审核材料，不自动发送或产生银行冻结效果。数字签名、JSON-LD、跨节点自动互认、外部接口熔断和真实资金自动托管不进入本批。消息/文件哈希用于完整性核对，不认证来源。

## 2. 请求、核验回执与生效信封

### 2.1 输入与可信字段分离

| 对象 | 必须绑定的内容 | 信任边界 |
| --- | --- | --- |
| SystemObjectMetadata | 对象 ID、节点/共同体归属、创建主体、时间、ACL、正整数修订号 | 由服务端创建或核验；请求不能替换归属、创建者或版本。秘密 Ballot 不保存身份性创建者，例外及关联隔离见 5.2；其他独立业务 ID 须与对象 ID 一致或有唯一映射。 |
| MandateClaimInput | 授权 ID/预期版本、目标 ID/预期版本、拟援引权能、幂等键 | 只是声明；命令路由决定所需权能，不由客户端选择更弱权能。 |
| AuthorizationCheckReceipt | command_id、attempt_id、幂等键、认证主体、授权版本/链、实际动作、目标版本、来源及状态观察时间、核验时间、保护令匹配结果、审查记录引用 | 服务端生成，应用层只追加；不是客户端可上传的生效凭据，也不宣称不可篡改。 |
| ActionEffectivenessEnvelope | 动作及目标版本、MandateRef、EvidenceRef 列表、ScopeSpec、RemedySpec、当前尝试的核验回执 | 服务端组装并验证字段相互一致；旧成功回执不能用于新动作。 |

请求不得设置 `authenticated_principal_id / actor_id / live_verification / auth_check_receipt` 等调用者或核验字段；与业务有关的受影响主体、代表对象另用明确字段表达，不能冒充调用者。认证中间件还须核对租户与对象访问权；定时任务使用有范围的服务主体。

核验结果至少区分 `VERIFIED_ACTIVE / EXPIRED / REVOKED / POWER_NOT_GRANTED / SCOPE_MISMATCH / UNKNOWN_MANDATE / SOURCE_UNAVAILABLE`。授权有效、保护令命中、计量不足和业务前置条件失败是不同维度；`VERIFIED_ACTIVE` 不等于整项命令已通过。人工审查使用 `institutional_review_ref`，不以字段名暗示已经实现数字签名。

### 2.2 强类型还需要语义约束

完整接口须在 AW-001 中形成机器可读契约和正反样例，至少表达以下条件，不能仅用 TypeScript 可选字段及注释代替：

- 生效信封中的证据引用非空、可解析且版本一致；程序决定也可引用程序事实，不强迫使用物理指标。
- 范围使用可核对的目标/组织标识、动作和资源种类、数量、单位；资源上限不只存自由文本。持续控制动作有明确到期或失效条件，保护令必须有到期时间。
- 通知接收者、可访问的异议窗口、复核主体和救济引用有效；不能用空数组或空字符串满足四元组。
- `EFFECTIVE` 的约束必须关联有相应权能的信封；`SUBMITTED` 可无该信封。`SUPERSEDED / WITHDRAWN` 不自动抹去既有义务或历史事实。
- 母体分母的精确值/区间/未知使用互斥结构；区间有序、计数非负。保留抽样框、分层、回应/未参与分类、时间窗口和支持措施，不能因简化接口丢掉参与审计原始信息。
- 发言的原文与译文许可、表达确认、表决实质性复核分别版本化。确认绑定精确文本版本；未确认的译文不能冒充当事人表达。
- 拒绝价值折算与退出讨论/子项表决分字段；沉默或未回答用未知状态，不推断成同意或拒绝。

### 2.4 实例级职责分离

AW-001 固定动作注册表绑定已公布的职责分离规则版本及实例范围，AW-002 在动作生效时核验。比较共同体内经核验关联账户的稳定 `member_id`，不能只比较当前角色或登录账号；关联方法及变更须可复核，不宣称能识别所有现实同一人，也不建立跨共同体实名库。

首个小额资助模板采用以下硬互斥；其他模板须在开轮前明确适用范围，不将资助审批回避泛化为普通成员不能参与民主表决：

| 动作与实例范围 | 必须排除的成员 |
| --- | --- |
| APPROVE_COMMITMENT，当前提案对应的资助承诺 | 该提案发起者；集体批准核对所有批准成员，不只核对最后提交人。 |
| VERIFY_EXECUTION_RECEIPT，当前工单 | 该工单的 AUTHORIZE_TICKET_HANDOFF 授权人及 RECORD_TICKET_HANDOFF 实际经办人。 |
| LIFT_PROTECTIVE_ORDER / RULE_BALLOT_MATERIALITY，受影响工单及关联轮次 | 直接被限制的经办执行人；提出保护请求不因此被禁止，签令仍另核权限与回避规则。 |
| ADJUDICATE_APPEAL，当前申诉 | 申诉人、被申诉决定的原签署人，以及按预先公布规则纳入的与该争议直接相关的提案、执行或保护令责任人；集合按下述规则留痕。 |

在案件 A 执行不妨碍在无冲突的案件 B 复核。同案更换账号、角色或由自己代表的另一席位操作不能绕过互斥；必要身份关联无法核实也不能视作已通过。缺少合格独立复核人时按既定程序暂缓或转介，管理员不得临时关闭检查。拒绝保留理由与救济入口；不借此引入未经授权的紧急豁免。

申诉回避集合随已核实责任关系累进更新，但不直接取全部上游血缘的人员并集。以被申诉动作/对象为起点，按开轮前确定的回避规则，核对相关提案人、原签署人、经办人及保护令签发人；保存规则版本、纳入理由、成员关联依据和责任记录版本。决定前重检，裁决者与适用回避集合交集非空或必要关联未核实，则不得裁决。仅作为无关证据作者或其他案件参与者，不因此自动被排除；回避判断可质疑，管理员不能自行删去冲突成员。

历史回放中无法映射的角色保留原始来源标识及 `UNMAPPED_HISTORICAL_ACTOR_NON_EXECUTABLE`，不得伪造已核验 member_id。导入操作者的真实认证身份与历史叙事中的行为人分开。沿用 `mode=simulation`，以 `historical_replay` 标明用途，不新增与 simulation/advisory/delegated 并列的模式；该导入记录不能原地升级为真实 delegated 执行依据。后来补齐身份映射只补充历史记录；真实行动须新建关联案件并重新核验身份、授权及全部门控。真实历史材料还须满足数据许可，不能送入只接受 synthetic 的现有 0.1.0 配置。

## 3. PostgreSQL 事务与并发边界

### 3.1 共用案件互斥锁与固定锁序

只锁“当前存在的活跃保护令”不能阻止空集合上并发插入新令。Batch 1 采用较保守的单案件串行化：所有该案效力命令，包括保护令的创建、解除、延期和关联对象变更，都必须锁定同一案件主行。以较低的单案并发换取更易验证的顺序；普通读取不因此全库加锁。[G21]、[G22]

候选实现固定使用 `READ COMMITTED`。命令预登记使用独立短事务；主业务事务按下列 0–4 级取得协调锁及适用领域锁，同层按租户及稳定 ID 排序。不是每条路径都访问全部层级，但禁止逆序；Outbox/导出读取放行的 Case 共享锁例外见 3.3。

| 级别 | 对象及锁模式 | 锁后检查 |
| --- | --- | --- |
| 0 | 唯一 CommandRecord：FOR UPDATE | 重检当前 attempt/generation、请求指纹及终态；同键 worker 和核对器不能只锁各自 attempt。 |
| 1 | 完整 AuthorityRecord 授权链：读取 FOR SHARE，修改 FOR UPDATE | 提前选择最强所需模式，避免先共享后升级；链结构或版本变化时重新规划整个事务。 |
| 2 | 所有目标 Case：FOR UPDATE，随后 Commitment：FOR UPDATE | 重检归属及覆盖关系；新令插入也经过案件行，新建案件由授权锁和唯一键控制。 |
| 3 | ProtectiveOrder：案件锁后重新查询，修改既有令 FOR UPDATE | 使用新的语句快照查询覆盖当前动作的保护令，不能依赖加锁前集合。 |
| 4 | FulfillmentTicket：FOR UPDATE | 重读版本、资源预留及阶段依赖；最终授权/时间检查后写效果、回执和审计再提交。 |

核对器的领域协调止于第 0 级，不为核对 IN_FLIGHT 先锁案件或工单。它在命令锁内更新 attempt/generation 和诊断仍可能取得相应数据库写锁；禁止其他路径持有这些子记录锁再反向等待 CommandRecord。禁止持 1–4 级业务锁反向获取第 0 级锁。完整登记及重试规则见 5.1。这是防止所述锁序反转的协议，不是“整个事务只锁一行”或死锁免疫保证；外键、审计写入及其他隐式锁仍纳入故障测试。

锁定目标包括案件/承诺对后代工单的适用关系，不能只比较请求中的一个 `target_object_id`。目标所属案件和覆盖关系必须在锁后核验；不能让移挂对象避开原案件的控制。跨案批量动作如未实现完整排序即拒绝，不能逐案部分提交后声称原子成功。所有业务写入角色必须通过相同服务路径，不以普通外键替代这个约定。

授权撤销和依赖它的命令通过授权行的冲突锁排序；保护令与交接通过案件行排序。两事务若均成功，其顺序应符合上述冲突锁协议；等待后必须重新检查状态，不能保留等待前查询结果。不承诺任意远程系统与本地数据库共同串行化。死锁、锁超时及事务重试仍须测试，固定顺序不是免除故障处理的证明。

### 3.2 时间与外部状态新鲜度

定义逻辑生效点为：持有所需锁、临近业务写入的最终检查时点；保存 `checked_at`，采用 `valid_from <= checked_at < valid_until`。不能把事务开始时的 `CURRENT_TIMESTAMP` 当作等待锁后的当前时间；PostgreSQL 对事务时间与实际当前时间有不同函数。[G23] 测试须覆盖长时间等待跨过授权或保护令到期点。

过期保护令即使后台尚未更新枚举，也不能继续阻断；是否有效同时查询状态、签发/生效时间和到期时间。到期任务仅记录已到期及升级待办，不再创设继续冻结权。新交接仍按独立前置条件核验，全部通过则可以继续。

Batch 1 的强并发保证限于本节点管理的授权与状态。外部资料记录来源、观察时间和允许新鲜度；需要新鲜状态但不可取得时拒绝新效力。一次远端查询不能消除查询后的远端撤销竞态。没有远端租约/协调协议时，不宣传全球实时撤销保证；相应接口属于后续专项。人工审查也不因为结果写入数据库就变成不可质疑的事实。

### 3.3 许可撤回与本地输出放行

修改发言发布许可或 GovernanceMarkings 的事务必须取得所属 Case 的 `FOR UPDATE`，同事务递增既有 `access_policy_version`。涉及授权的修改仍先取得命令/授权锁；不同写路径不能各用一套锁序。派生物和缓存记录其依据的策略版本，版本不一致时重新核对当前上游许可，不能只信旧标记。

Outbox 领取任务的短事务先结束；最终输出放行事务取得 Case `FOR SHARE`，重新检查策略版本、上游许可、收件人权限和用途，绑定精确输出版本及最小放行记录。导出器遵循相同规则。若需修改 Outbox 状态，在案件锁后获取其行锁；不得持有 Outbox 行锁等待案件锁，形成相反锁序。输出无权限或依赖无法核实时不放行。

保证限定在**本地最终输出授权/放行点**：撤回先提交，后续放行必须拒绝；放行在先，记录该顺序及可能已在途的输出。案件锁不跨外部网络 I/O 持有，也不能让数据库与消息接收方原子提交；本地放行记录不等于外部已送达。通知优先仅含不泄露案件敏感信息的提示和需重新鉴权的链接，读取正文时再查许可。外部发送未知进入核对，已经收到的正文、下载包和截图无法保证撤回。

通知的业务载荷固定为受控引用 `{ case_id, target_object_id, event_type, recorded_policy_version }`，不存证词、译文、摘要正文或敏感标题；收件人、尝试及投递状态另作受控元数据。这些内部 ID 也不直接成为公开通知正文。消费流程固定为“短事务领取 → 结束领取事务 → 案件共享锁内重验并登记本地放行 → 提交后发送通用提示及鉴权链接”。不得把内部 payload 原样发给未获准接收者；点击链接时重新鉴权渲染，旧 recorded_policy_version 不授予访问权。

导出采用下列待实现伪代码契约；“短事务”是目标，不承诺毫秒级延迟：

```text
prepare:
  按当前权限读取固定对象版本及策略版本 V1，记录输入清单
  不持案件排他/共享行锁，在私有存储渲染 staging 文件
  完成文件写入及摘要核对，固定不可变文件引用；此时不可供下载
publish_local:
  BEGIN
  按适用锁序取得 Case FOR SHARE，再取得待发布包记录锁
  重验当前策略版本 == V1、上游许可、请求者/接收者权限及导出范围
  若不满足：不发布；COMMIT 后清理暂存或按当前权限重新准备
  若满足：登记文件引用、输入/策略版本及放行记录，状态 PUBLISHED_LOCAL
  COMMIT
download:
  按当前许可重新检查包及其上游依赖，通过才在锁释放后传输
```

暂存文件从创建起即受 ACL 和保存/清理规则保护；版本变化不导致受限内容先公开再删除。发布事务只登记已完成文件的元数据，不移动文件或进行对象存储网络请求。`PUBLISHED_LOCAL` 仅表示受控文件已登记可用，不等于永久公开、已下载或真实机构已批准。下载不能绕过鉴权使用公开静态地址或可独立访问敏感正文的长期链接；发布后撤回也须阻止新的下载放行。已放行的在途下载仍受前述能力边界限制，文件缺失或发布结果未知按记录核对，不凭暂存文件存在宣称成功。

## 4. 单一保护令权威源与并行状态

保护令是**临时暂停效力**的唯一权威记录，不是所有业务拒绝的唯一原因；授权、资格、底线、资源和阶段前置条件仍独立检查。阻断条件是存在至少一条当前有效、覆盖动作及目标的保护令；这是“任一命中即阻断”，不要求所有保护令都命中。

| 对象 | 状态与职责 | 必须保持的分离 |
| --- | --- | --- |
| Case | INITIATED、DELIBERATING、FROZEN_FOR_BALLOT、DECIDED、CLOSED；可记录无协议并开新轮次 | 阶段导航不代表履约或复核完成。 |
| Appeal | SUBMITTED、ADMISSIBILITY_REVIEW、ADJUDICATING、RESOLVED | 不设 STAY_GRANTED 状态作为阻断条件；获准暂停时关联独立保护令。 |
| ProtectiveOrder | ACTIVE_HOLD、EXPIRED_NO_LONGER_BINDING、LIFTED_BY_DECISION、SUPERSEDED_BY_NEW_ORDER | 生效前为请求记录；解除一个令不影响其他令，期限不依赖后台任务及时执行。 |
| FulfillmentTicket | QUEUED_INTERNAL、BLOCKED、READY_FOR_HANDOFF、HANDED_OFF_TO_EXTERNAL、EXTERNAL_RECEIPT_LOGGED、CANCELLED | 阻塞原因是可重算视图/缓存，不能代替权威检查；已交接不再伪装为内部可冻结。 |
| Commitment | ACTIVE、PARTIALLY_FULFILLED、COMPLETED、TERMINATED_BY_AMENDMENT | 总体义务与分期工单分离；每期的资源、依赖、回执和未履行余额独立核验。 |

一个承诺可以对应多张工单。取消工单只取消该交接安排、按规则释放受控预留；不把未履行义务当作已完成或自动扣减。变更承诺总额或义务另需 `AMEND_COMMITMENT`。只有独立核验的实际履行才计入已履行额，外部回执上传不自动证明结果真实。

`AUTHORIZE_TICKET_HANDOFF` 只可建立有期限、绑定版本的就绪资格；实际交接前仍重检。`RECORD_TICKET_HANDOFF` 由有权人员确认真实人工交接，记录接收方、交接时间及依据，才标记 `HANDED_OFF_TO_EXTERNAL`；数据库不声称对外部人类行动提供原子控制。事后报告已经发生但未获授权的动作，应另记事件和补救，不能拒绝记录事实或补造合法授权。

拒绝请求不能顺便修改目标状态来实现“防护”。BLOCKED 原因可在读取时重算；若物化缓存/维护工单，须由有范围的系统任务另行审计，不能让无权限调用者通过一次失败请求改变他人的对象。

## 5. 三路审计、幂等与不确定结果

| 路径 | 事务与回执 | 故障边界 |
| --- | --- | --- |
| A：APPLIED | 业务新版本、当前核验回执、命令结果、审计及需要的待通知记录同事务提交 | 审计写入失败时整个事务回滚，不返回成功。 |
| B：REJECTED | 不改变目标业务表；提交拒绝回执和最小审计，保存核验依据的版本/时间与原因 | 可在未做业务写入的当前事务正常提交；若另开写事务，原判断必须绑定历史尝试，不能冒充新事务的实时核验。 |
| C：SYSTEM_FAULT | 能确定未提交时回滚；独立受控故障日志记录请求/尝试 ID、错误类别、时间及恢复状态 | 同一数据库的第二连接池仍可能一起不可用；最后可输出 stderr/告警，但不能保证告警已被接收。 |

连接在 COMMIT 响应前中断可能意味着“结果未知”，不能直接宣称已回滚。`OUTCOME_UNKNOWN` 是应用观察与核对状态，不是已确定的数据库业务结果；异常处理不得无条件覆写可能已提交的 APPLIED。先按 5.1 核对，禁止盲目再次交接。只有确认未提交才重试。故障通道失效时不报告“已存证”，不因此放行业务；不自建并宣称等同 PostgreSQL WAL 的持久化系统。[G24]

幂等唯一键包含共同体、主体、命令类型及客户端键，绑定规范化的请求指纹；规范化规则在接口契约中固定，不宣称 JCS 合规。敏感请求指纹按 5.2 保护，不默认采用可枚举的裸 SHA-256。相同键不同内容返回 `ERR_IDEMPOTENCY_CONFLICT`。已提交成功的相同请求返回既有结果，不再次生效；读取回执仍检查当前访问权。规则性拒绝作为该键的终态，补材料或重授权后用新键；授权源不可用、确定回滚等可重试故障允许同键同内容建立新 attempt，保留历次结果。结果未知时先核对，不自动套用可重试分支。

审计只保留必要的对象/版本、字段名、责任主体及受控元数据。低熵敏感值的公开 SHA-256 摘要可能被猜测，不能把哈希当匿名化；敏感内容和对应摘要均按权限和保存计划处理。业务变更与日志的同事务保证不等于管理员无法篡改，恢复演练和独立副本仍需验证。

### 5.1 命令预登记与结果核对

预登记增加尝试的可追踪性，不单独证明请求已执行或解决幂等。AW-002 采用以下有限流程，不引入分布式事务框架：

1. 通过基础认证、归属检查和限流后，用独立短事务按上述唯一键创建 `CommandRecord` 及初始 `CommandAttempt`，保存受控请求指纹、当前 attempt/generation 和 `IN_FLIGHT`。重复键先读取既有记录；预登记本身回包丢失，也按唯一键核对，不能另起一个逻辑命令。登记仅是请求元数据，不改变目标对象效力。
2. 主业务事务首先取得该 CommandRecord 行锁；重检内容、终态和当前 generation，迟到旧 worker 不得继续。再按第 3 节加锁及核验，业务效果、APPLIED 审计、回执与命令结果同事务提交；规则拒绝按路径 B 登记，不修改目标业务。
3. 核对器从权威可写数据库取得**同一命令行锁**，不用可能延迟的只读副本。若获取失败、仍被运行中的事务占用或数据库不可达，保持结果未知。客户端连接销毁或无锁查询看到 IN_FLIGHT 均不是回滚证据；IN_FLIGHT 也不证明主事务已经开始。
4. 锁后发现 APPLIED，按当前访问权限返回原回执；发现终态 REJECTED，返回原拒绝。若仍为未决且依本协议不存在已提交业务效果，核对器在持锁期间关闭旧 attempt 为 `ABORTED_RETRYABLE`，推进 generation，使迟到旧 worker 失去写入资格；随后才允许同键同内容的新 attempt。所有成功效果与命令结果必须原子提交，否则不能据此判定可重试。

命令结果是效果核对依据，attempt 诊断保留观察历史；两者不能由异常处理互相覆写。该流程只控制本地业务，人工交接和外部投递仍有各自的事实记录与对账边界。

超时只是启动核对的条件，不是判定未提交的依据。核对器依 3.1 的第 0 级协议关闭旧 attempt 并推进 generation，不取得 1–4 级业务锁；拿不到命令锁时保持未知。测试必须包括 worker 尚未取得命令锁即被核对器围栏失效，以及 worker 已持锁且 COMMIT 回包丢失两种顺序。

### 5.2 秘密选票与私人偏好的审计例外

秘密 Ballot 是通用创建者元数据的显式例外：不保存身份性的 `created_by_principal_id`。身份侧审计记录某成员在 DecisionRound 中消耗了资格（BALLOT_CAST），不记录生成的 ballot_id、选项或内容摘要；资格动作的核验回执/信封绑定轮次及资格对象。选票存储仅保留计票所需的轮次、内容和受控技术元数据。资格消耗与有效选票写入仍在**同一事务**内成功或失败，必须同时防止资格耗尽却无票、重复票与重复重试生效。

隔离不仅是删一列：command_id、attempt、幂等结果、授权回执、请求/APM 日志、精准时间戳和导出关联都须检查。身份侧回执不携带可连接到内容侧的选票标识；普通审计角色不能联查内容存储或技术关联，选票正文不得进入通用日志。私人 Preference 保留其所有者 ACL，不机械删除归属来伪装匿名。

AW-001 的 DDL/仓储契约须明确以下要求，AW-004 才实现并验收；当前没有对应数据库实现：

- ballots 主键使用由安全随机源生成的 UUIDv4，不使用 SERIAL/BIGSERIAL、自增序列或时间有序 UUIDv7；不另存可对齐身份侧的插入序号。
- ballots 不保存逐票精确 created_at；默认只关联 decision_round_id。若需展示时间，只提供轮次共用的关闭窗口信息，不记录可还原逐票次序的细分桶。资格/截止时间在写入时核验，不能靠事后删除时间字段补救越期投票。
- 投票成功的业务响应和幂等缓存限 `{ round_id, eligibility_status: "BALLOT_CAST" }`，不含 ballot_id、选项、内容摘要或内容存储定位符。受控诊断 ID 也不能暴露身份侧与票面侧的连接。
- 普通审计角色通过受控接口/视图访问，不授予选票基表直接查询、数据库系统列、事务元数据或原始物理备份的访问权；导出应用相同限制。表的默认字段、触发器和日志也须纳入检查。

这些措施减少可见关联，不能消除底层侧信道。PostgreSQL 的 `xmin` 标识行版本的插入事务，同事务记录仍可能被高权限主体关联；去掉 created_at 或改成 UUIDv4 不改变这一事实。[PostgreSQL 系统列说明](https://www.postgresql.org/docs/18/ddl-system-columns.html) 普通角色的接口隔离与数据库运维的信任假设必须分别验收、披露。

普通审计不保存秘密选票或未公开偏好的内容摘要。受控存储确需完整性或幂等指纹时，使用带秘密密钥的 HMAC-SHA256，例如 `HMAC-SHA256(key=K, data=encode(domain, nonce, canonical_payload))`；固定无歧义编码与规范化、足够随机的逐记录 nonce、密钥版本和保存期限。K 是独立秘密密钥，nonce 不冒充密钥；nonce 随受控材料保存，密钥另由受限密钥管理保护。校验相同请求复用登记的 nonce/密钥版本，普通日志不公开可枚举裸哈希或密钥材料。HMAC 不加密内容，正文仍须受控存储；不用新密码协议替代现有访问控制。

Batch 1 只承诺普通参与者及普通审计角色不能通过产品接口/导出直接连接身份和选票内容；不宣称能对抗数据库超级用户、应用服务串谋、底层事务/流量与时间相关性分析，也不提供密码学不可关联或抗胁迫保证。AW-001 必须列出可访问上述技术元数据的运维信任边界，AW-004 在该边界内验收。

## 6. 计量、表达、参与和恢复契约

### 6.1 时间分桶与方向判定

保留高频原始观测；有效样本按固定 UTC 窗口和分桶起点归桶，区间采用左闭右开。首版固定窗口长度为桶长整数倍，不静默生成部分桶；时间戳采用观测时刻并记录接收时刻。去重、质量合格、有效覆盖与迟到修订规则必须明确；一桶的密集样本不能填补其他桶。

`min_valid_bucket_coverage_ratio` 在 0–1 范围，计数与缺口为非负整数，时长为正数。分别计算首部、内部和尾部缺口；覆盖不足返回“证据不足”，不是已发生违规。延长观察窗口生成新评估版本，不覆盖原窗口或无限等待。有效桶覆盖率不证明桶内每一时刻都被观测，结论必须限定到所定义的采样和聚合方法。

上限判据 LT/LTE 对应上界，下限 GT/GTE 对应下界；区间判据明确端点是否包含。WITHIN_BAND 要求整个适用区间落在允许范围内，OUTSIDE_BAND 的保守判据要求区间完全位于禁区一侧；横跨禁区或方法不支持时为不确定。点估计仅可在预先批准的方法下使用，不得作为缺少不确定性资料时的自动降级。注明区间是测量不确定性、统计置信区间还是其他边界及其计算来源；不能仅填写 0.95 就获得统计含义。

测试用虚构业务阈值和单位，不借未声明物质口径的“10 mg/L”示例宣称饮用水标准。方法、缺失和聚合结果须可复算；情景预测不满足约束与现实违规仍分开。

### 6.2 表达与参与

撤回展示许可可依有效发布政策立即停止后续展示并保留受控版本记录；原文无许可则显示脱敏占位。确认撤回不自动等于所有内容许可撤回，需记录具体请求与政策。是否影响表决是独立裁定；普通评论不因撤回而自动取得暂停权。裁定重大影响使用 `RULE_BALLOT_MATERIALITY`，签发暂停还需要 `ISSUE_PROTECTIVE_ORDER`，令应覆盖具体轮次及计票/发布动作。

参与审计允许 `MET / BELOW_REQUIRED_FLOOR / INDETERMINATE_INSUFFICIENT_DATA / NOT_YET_EVALUATED`。不确定或不足超时进入升级等已授权处理；`PROCEED_WITH_DISCLOSURE` 必须引用适用于当前非核心缺口的预授权及具名审查，不能作为任意缺口豁免。无缺口豁免也不阻止提出异议。

### 6.3 恢复与保留

恢复清单保留四个独立维度：资料是否完整/受限遮盖/缺失/损坏、摘要与来源认证分别如何核验、当前程序效力、外部控制重绑定。Batch 1 来源认证为 `NOT_SIGNED_BATCH1_BASELINE`；不实现签名验证器，遇到其他签名方案报告未支持并隔离，不相信导入包自报的 `SIGNATURE_VALID`。

SHA-256 清单只能与持有的基准核对内容，攻击者同时替换文件和清单仍可能匹配；没有可信归档来源时不能据匹配恢复执行。摘要不匹配时隔离受影响记录，不将损坏内容当作可信历史展示；已验证的独立记录可依权限只读。效力由接收环境的有权人员逐项确认，不实施自动 Comity。重绑定成功也不跳过本地授权、保护令、前置条件及旧端停止新交接的确认。

保留抽样原始依据、定性异议与按类别制定的保存/销毁计划；最新接口摘录不能删除此前已有的这些要求。`ARCHIVE_SEAL` 是受限保留，不是销毁；匿名化和密钥销毁的效果须验证，哈希不自动匿名。独立节点的实时双重履约防护属于 Batch 2，本批仅做受控人工恢复演练。

## 7. 错误与处置结果

基础错误沿用 `ERR_UNAUTHENTICATED_CONTEXT / ERR_INCOMPLETE_FOUR_TUPLE / ERR_UNAUTHORIZED_POWER / ERR_MANDATE_LAPSED_OR_REVOKED / ERR_MANDATE_SOURCE_UNAVAILABLE / ERR_BLOCKED_BY_PROTECTIVE_ORDER / ERR_INCLUSION_SHORTFALL_UNRESOLVED / ERR_INSUFFICIENT_TEMPORAL_COVERAGE / ERR_EXPIRED_ORDER_NO_LONGER_HOLDS / ERR_HANDOFF_PRECONDITIONS_UNMET / ERR_MATERIALITY_THRESHOLD_NOT_MET / ERR_VERSION_CONFLICT / ERR_IDEMPOTENCY_CONFLICT`。范围不匹配、未知授权、跨租户访问等内部原因不得在公开回执中泄露私密对象存在性；对外映射在接口冻结时固定。

域拒绝、系统故障、待核对结果分别返回，不把所有失败都包装成制度性否决。回执包含获准披露的理由、相关版本、补充或救济入口及是否可重试；未落盘时不能返回持久回执承诺。公开错误码与内部诊断之间保留可审计关联。

### 7.1 对象与动作增量的约束

固定动作注册表只描述已审阅的处理器和权限映射，不能以可选布尔值、校验器列表或自定义锁序绕过内核。Action ID 与 required powers 分开；不存在“选择较弱动作配置即可生效”的通道。

血缘清单不产生暂停效力；已记录核心依据变化可触发复核，无边也允许提出遗漏。访问限制、发布许可、来源确认与保存计划分别处理；许可收紧后即使影响遍历未完成，受控读取仍核对当前策略，不能泄露旧缓存。冻结快照原文不覆写，脱敏导出另成版本。具体字段及一致性见 [增量第 3–4 节](ontology-actions.md#3-多维标记与派生资料控制)。

AI 服务权限受请求者、案件、用途和任务委托共同限制，Batch 1 仅提出 DRAFT，人类确认后受理；服务不能使用人类受托人的全量权限。方案分支只比较固定基线和允许改动的参数，不自动 rebase 或合并成生效决定。模板安装、软件发布和数据迁移都不产生新制度授权。

Outbox 与业务同事务登记，消费前重新核对当前权限和许可；重试不新增制度效力，未知投递结果核对后处理，不承诺外部 exactly-once。新增策略缺失、依赖不完整、分支过期与未知配置等内部原因及对外错误映射并入 AW-001；不暴露敏感对象存在性，也不把未确定策略解释为已发生违规。

## 8. 正反成对验收矩阵

### 9.3 后续切片与 Slice 2 的实施入口

剩余 AW-001 契约按 [Slice 2 实施方案与路线图](aw001-slice2-plan.md) 分批交付，主方案 v0.7、Slice 1 已验证实现及原 FT/PT-01..20 编号保持不变。Slice 2A 前置 CommandRecord/Attempt/Result 与三路审计结构，并实现保护令三动作及时间/覆盖判定；2B 完成承诺与工单六动作，独立核验记录不新增 TicketStatus.VERIFIED；2C 补齐申诉四阶段与 RC 2.4 集体/实例级回避。Slices 3、4 分别承接参与/计量/表达/选票例外及标记/依赖/分支/AI/恢复/模板契约。

多对象跃迁只递增合法写集合中的对象版本，保留其他对象和历史信封；正确 REJECTED 结果不得改写业务对象。来源不可用的可重试处置与规则性终态拒绝分开，提交结果未知不得假称已回滚。离线夹具有效不等于所记录命令获准；三路结果和适用成员映射均须独立核对，而非相信夹具自报。
